# Rigging a headless body

Researched 10 Oct 2026 across four independent angles — Mixamo itself, rival
auto-riggers, Blender-native routes, and the head-to-body join — with every
load-bearing claim adversarially re-checked against primary sources. 38 approaches
surveyed; **9 of 24 checked claims did not survive refutation** and are listed at the
end so nobody reinstates them.

---

# Decision: bind every piece to one donor Mixamo armature in headless Blender. Do not auto-rig the bodies at all.

The five requirements are not one problem. Names (1), the 65-bone set (2), the rest pose (3) and a usable Head bone (5) are all properties of *an armature* — a fixed asset you obtain once. Only skin weights (4) are per-piece geometric work. Every route that tries to solve all five per piece (Mixamo markers, MIA, Tripo, AccuRIG) pays for a skeleton you already have, and most of them then hand back bone names or a rest pose you have to repair.

The clincher is scale: ~9 characters × ~10 pieces ≈ 90 meshes. Mixamo's auto-rigger takes one mesh and needs a human to drag 8 markers per upload. The donor route costs **one browser session, ever**.

---

## 1. The route — what you run tomorrow

**Step 0 — one manual browser session (the only one).**
On mixamo.com: load a stock character. Download it as **FBX Binary, Pose = T-pose, With Skin**. Then download your clip set as **Motion, FBX Binary**, downloaded *for that same character* (every Mixamo export is built for a `character_id` and retargeted server-side, so clips and donor come from the same rig by construction). Commit the FBX files.

Take the **with-skin** character download, not a "Without Skin" motion, as the donor. Blender's FBX importer builds bone rests from `Pose`/`BindPose` and skin `Cluster` data and silently falls back to raw node transforms when neither exists (`bind_matrix = self.matrix.copy() if self.matrix else None` in `scripts/addons_core/io_scene_fbx/import_fbx.py`). A skinless file has no cluster and no bind pose, so its rest pose is whatever the exporter happened to write. The with-skin file provably carries a bind pose.

**Step 1 — build `donor.blend` once, with pinned import settings.**
Import the character FBX with explicit flags written into the script and never changed again: `automatic_bone_orientation=False`, `ignore_leaf_bones=False`, `force_connect_children=False`, `primary_bone_axis='Y'`, `secondary_bone_axis='X'`, fixed `global_scale`. FBX joints carry no Blender roll, so these flags *are* the rest pose — this is why "the donor reproduces Mixamo's rest pose" is only true if donor and clips are imported identically and the armature is never edited in Edit Mode.

Keep **both** the armature and the stock mesh (mesh hidden, in its own collection — it is your weight source). Dump `name / parent / matrix_local / use_connect / use_deform` per bone to JSON as a regression fixture.

Then **count the bones and read the names, do not assume**. The 65 figure is in Mixamo's public client bundle, and 25 + 5×4×2 = 65 closes against all four of Adobe's LOD counts — but that arithmetic implies the fingertip `*4` leaves are included and no eye bones exist, and nobody has verified what a *stock* character actually ships (its Skeleton LOD was never offered to you). If the donor comes in at 52, append the 13 zero-length leaves by script; if it carries `LeftEye`/`RightEye`, decide then whether to keep them.

**Step 2 — load the clips onto the donor** with the same import flags, and eyeball one walk cycle. If limbs explode, your flags are inconsistent, not your mesh.

**Step 3 — per piece, fully unattended (`blender -b -P bind.py`).**
1. Import the generated pieces (GLB).
2. **Align**: uniform scale to the donor's height, translate so hips/stump land on the donor's. This is the load-bearing step — see §2.
3. Add an Armature modifier pointing at the donor armature. Transfer weights from the hidden stock mesh:
   `bpy.ops.object.data_transfer(data_type='VGROUP_WEIGHTS', use_create=True, vert_mapping='POLYINTERP_NEAREST', layers_select_src='ALL', layers_select_dst='NAME', use_object_transform=True, use_max_distance=True, max_distance=…, ray_radius=…, mix_mode='REPLACE')`.
   `layers_select_dst='NAME'` is mandatory — `'INDEX'` shuffles 65 groups.
   Prefer this over bone heat (`ARMATURE_AUTO`): bone heat has a developer-confirmed open bug (#84609) on very small faces, which is exactly what image-to-3D output is, and on failure it `break`s the per-bone loop and leaves every later bone empty behind an `RPT_WARNING` that still reports success.
   For rigid pieces (hat, belt buckle, pistol): parent with `ARMATURE_NAME` (empty groups) and script-assign weight 1.0 to the one bone.
4. **Handle the neck stump explicitly, do not hope.** Select vertices within a small radius of the open boundary loop and assign them to `mixamorig:Neck`/`mixamorig:Head` by script. Nearest-donor-surface for a neck cap is jaw or skull interior; `max_distance` will leave those vertices unweighted, and **an unweighted vertex in a rigged mesh is a hard glTF export failure**, not a cosmetic one. This also gives `mixamorig:Head` real weighted vertices, so no downstream "remove unused bones" pass prunes it.
5. Clean: `vertex_group_clean`, `vertex_group_limit_total(limit=4)`, `vertex_group_normalize_all`, then **assert zero unweighted vertices** and assert weight sums ≈ 1.0 (glTF validator threshold is 2e-7 × non-zero weights).
6. Export GLB with `export_rest_position_armature=True`, triangulate in Blender, bone influences = 4.

**Step 4 — Godot.** Expect **`mixamorig_Head`**, not `mixamorig:Head`: both the glTF and FBX importers run `_sanitize_bone_name` → `bone_name.replace(":", "_")`. Any `BoneAttachment3D.bone_name` or hand-written Skin bind must use the underscore form. Leave Rest Fixer / Overwrite Axis **off** — you are already on one shared armature, and Godot's own docs warn it "can produce horrible results" when the external rest matters.

The attached head: two `MeshInstance3D` on one `Skeleton3D`, the head skinned to `mixamorig_Head`/`mixamorig_Neck` in the same rest pose. `BoneAttachment3D` is the cheaper fallback but is rigid at the seam.

## 2. The single biggest way this fails

**The generated bodies are not in the donor's pose or proportions, so the donor bones do not sit inside the mesh — and then the weights are wrong everywhere, not just at the neck.** The Armature modifier stores no bind matrix; the bind is implicit in rest-position-versus-mesh-coordinates. If the image-to-3D output is A-posed, or has cartoon-pirate proportions (short legs, barrel chest, huge hands), uniform scaling will not rescue it, and `data_transfer` will cheerfully map a thigh onto a forearm.

**Cheapest experiment — under a minute, locally, before you build anything.**
A ~40-line headless Blender script on one real generated body:

```
blender -b donor.blend -P fitcheck.py -- body_01.glb
```

1. Import the body, uniform-scale to donor height, align hip height.
2. For each of the donor's bone heads: `mesh.closest_point_on_mesh(p)` → report signed distance and inside/outside (normal dot test, or ray-parity). **Pass = every bone head inside the surface.**
3. Compare chain lengths — shoulder→elbow→wrist, hip→knee→ankle, spine — against the same chains measured from the body's silhouette. **Pass = within 10%.**
4. Print the worst offenders by name.

That one number set decides the whole pipeline, and it costs you nothing. Run it on one body before writing `bind.py`.

(Run it on a *real* output from your image-to-3D service, not a test humanoid. The whole point is whether *that* generator's proportions fit.)

## 3. Fallback, and the trigger

**Trigger — switch if any of:** more than two bone heads fall outside the mesh after scale+hip alignment; any limb chain deviates >15%; or the bodies are not T-posed at all.

**Fallback: Make-It-Animatable (MIA) as a joint-position estimator only, not as the rigger.**
MIA predicts joints and weights against a hard-coded 52-bone template with `MIXAMO_PREFIX = "mixamorig:"` and `assert len(MIXAMO_JOINTS) == 52`, so the Head bone is *emitted unconditionally rather than detected* — which is precisely the property a headless body needs. MIT code, Apache-2.0 weights, runs on the 4060 Ti, and there is a ComfyUI node (`MIA: Auto Rig` in ComfyUI-UniRig).

Use it like this: take MIA's predicted joint positions, write them into a **copy of the donor armature** in Edit Mode (keeping the donor's names, parents and the 13 leaves), and take MIA's weights. You now have a correctly-fitted per-body rig whose rest pose is no longer Mixamo's — so retarget the clips once per character with Blender constraint-and-bake (Copy Rotation on every bone, both spaces World, then bake), which is naming- and rest-pose-agnostic and is exactly what Auto-Rig Pro's Remap and Rokoko's retargeter do internally.

**Do not** fall back to Mixamo + stand-in head. It fails the unattended requirement outright (one marker session per piece × 90), it only rigs one mesh at a time, and the weights it computes around the neck are solved for a dummy head you then delete.

**Second-order fallback** if MIA's Neck/Head land at or below the stump: keep MIA for the body chain and hard-set Neck/Head from the head mesh's own geometry.

## 4. Genuinely unknown

- **What bone set a stock Mixamo character download actually carries.** The Skeleton LOD dropdown is not offered for pre-rigged stock characters. No evidence found. Count it on arrival.
- **Whether Mixamo's 65 includes the fingertip leaves.** The 25/41/49/65 arithmetic says yes, and Make-It-Animatable's file names exactly 13 commented-out leaves — but Adobe publishes no bone list anywhere, and the same file flags eye bones as a further excluded group, so the 65 may be a variant without eyes. Inference, not fact.
- **Where `mixamorig:Head` belongs on a body with no skull.** No vendor documents a rule, offset or proportion. HumanIK's "last full bone in the neck chain" presumes head geometry to measure against. The attached head's apparent pivot *is* that bone's origin, so a Head joint at the stump makes the head swivel about the neck base. For a human-proportioned body scaled to the donor this is free; for a big cartoon pirate head it is a design decision you will have to make deliberately, derived from the head mesh, not the body.
- **What Mixamo writes into a skinless motion FBX's node defaults.** The importer's fallback mechanism is source-confirmed; Adobe's file contents are not. This is why the recommendation is "use the with-skin download because it provably carries a bind pose", not "the skinless download is wrong".
- **Whether `data_transfer`'s `POLYINTERP_NEAREST` is good enough on hands.** Differently-shaped fingers are where nearest-surface mapping goes wrong first, and no primary source quantifies it. If fingers tear, the published fix is Robust Skin Weights Transfer via Weight Inpainting (SIGGRAPH Asia 2023, MIT) — confidence-gated copy plus interpolation for everything else — but it is reference code, not a tool, and **no evidence found** on its behaviour at an open boundary, which is exactly the stump rim.
- **Whether Mixamo would accept a headless mesh at all.** Adobe's FAQ requires "distinguishable head, body, arm, and leg areas", but no Adobe source documents what actually happens on submission — no error string, no failure stage. Moot on this route.

**Blender's Armature modifier binds a bone to geometry purely by matching names ("bones of a given name will deform vertices which belong to vertex groups of the same name. E.g. a bone named 'forearm', will only affect the vertices in the 'forearm' vertex group."), with no stored bind matrix and no mesh-side skeleton identity, which is what makes reusing an existing armature on a new mesh legitimate rather than a hack.**

- The quoted sentence is genuinely on the current page (docs.blender.org/manual/en/latest/modeling/modifiers/deform/armature.html, which serves the Blender 5.2 LTS manual) — I downloaded the page and extracted the article body rather than trusting a summary, so the wording is confirmed verbatim for the current version. Everything the claimant built on top of it is not supported.

1. "Purely by matching names" is contradicted by the same page. The name-matching sentence sits under "Bind to > Vertex Groups" and is prefixed "When enabled" — it describes one of two bind methods, controlled by a toggle. The other documented method, Bone Envelopes, deforms vertices near a bone according to that bone's envelope radius and distance, i.e. by proximity, with no name involvement; both toggles can be on at once (the manual's own skinning example shows the same pose solved by envelopes instead of vertex groups). Name matching is also not sufficient: bones flagged non-deforming are excluded regardless of a matching group name. The manual's Armature Deform Parent page states that vertex groups are only created for bones set up as deforming (https://docs.blender.org/manual/en/latest/animation/armatures/skinning/parenting.html), and the source confirms it skips channels whose bone has BONE_NO_DEFORM (source/blender/blenkernel/intern/armature_deform.cc, get_armature_deform_params, around line 341, right after the name lookup BKE_pose_channel_find_name(ob_arm.pose, dg.name)).

2. "No stored bind matrix" is not stated anywhere on the offered page — the page has no note on bind pose, bind matrix or rest position other than Preserve Volume's remarks about rotations away from rest position — and it is wrong as a statement about the engine. A rest/bind reference does exist; it is stored armature-side, not mesh-side. Blender's own source documents the relation pose_mat(b) = arm_mat(b) * chan_mat(b) (source/blender/blenkernel/intern/armature.cc, around line 2713), with BKE_armature_mat_pose_to_delta inverting arm_mat (the bone's rest matrix) to produce the deform matrix; the vertex deform then applies pchan.chan_mat per vertex (armature_deform.cc, BoneDeformLinearMixer::accumulate, line 119). The Python API documents the same rest matrix as Bone.matrix_local, "4x4 bone matrix relative to armature" (https://docs.blender.org/api/current/bpy.types.Bone.html), and convert_local_to_pose explicitly calls matrix_local "the custom rest matrix of this bone". On top of that, the deform converts between spaces using the live object world matrices (armature_deform.cc, target_to_armature / armature_to_target, lines 359-362), so the mesh object's transform relative to the armature matters too — and for Ctrl-P armature parenting that relative transform is frozen into the object's parent inverse matrix at bind time. What is defensible is only the narrow version: the mesh datablock itself stores no skeleton reference, just vertex groups and weights (the armature pointer lives on the modifier). The offered page does not say that either.

3. "Which is what makes reusing an existing armature on a new mesh legitimate rather than a hack" is the claimant's inference. The documentation says nothing about reuse being legitimate or otherwise, and the engine facts above make reuse conditional, not free: it works only when the new mesh is modelled in the armature's rest pose and positioned the same way relative to the armature, because the rest matrices it deforms away from are the existing armature's.
- Correct version: Blender's current manual (5.2 LTS) does state, under the Armature modifier's "Bind to > Vertex Groups" option and prefixed "When enabled", that bones of a given name deform vertices in the identically named vertex group, with the forearm example. That is one of two documented bind methods — Bone Envelopes instead deforms nearby vertices by envelope radius and distance — and even with Vertex Groups enabled, bones flagged non-deforming are skipped. The manual says nothing about bind matrices or mesh-side skeleton identity. In fact a bind reference does exist, stored on the armature rather than the mesh: each bone's rest matrix (Bone.matrix_local / arm_mat) is inverted against the pose matrix to produce the per-bone deform matrix, and the object-to-armature space conversion uses the two objects' transforms (frozen into the parent inverse at Ctrl-P time). What is true is that the mesh data itself carries no skeleton binding, only vertex groups and weights, so reusing an armature on a new mesh is mechanically supported — but it is conditional on the new mesh matching that armature's rest pose and relative placement, and no Blender documentation frames it as legitimate or as a hack.

**Linear blend skinning computes a vertex's deformed position purely from its own position, joint indices, weights and the joint matrices (jointMatrix(j) = globalTransformOfJointNode(j) * inverseBindMatrixForJoint(j), summed by weight). Two separate meshes bound to the same skeleton therefore deform identically at a seam if and only if their seam vertices have identical positions, identical joint indices and identical weights.**

- Two halves, different outcomes. FIRST HALF CONFIRMED. The offered page does state, verbatim: "jointMatrix(j) = globalTransformOfJointNode(j) * inverseBindMatrixForJoint(j);" with skinMat as the weight-scaled sum of u_jointMat[a_joint.*] applied to a_position, and "The transform of the node that the skin is attached to is ignored." The normative spec (Specification.adoc, main branch, glTF 2.0) agrees in substance: glossary "linear blend skinning:: A skinning method that computes a per-vertex transformation matrix as a linear weighted sum of transformation matrices of the designated nodes"; §3.7.3.3 "To apply skinning, a transformation matrix is computed for each joint. Then, the per-vertex transformation matrices are computed as weighted linear sums of the joint transformation matrices. Note that per-joint inverse bind matrices (when present) MUST be applied before the base node transforms"; §3.7.3.2 "Only the joint transforms are applied to the skinned mesh; the transform of the skinned mesh node MUST be ignored." So the omission of the old inverse(globalTransformOfMeshNode) term is correct for current glTF, not stale. Note the offered source is a tutorial in KhronosGroup/glTF-Tutorials — official but non-normative; the spec is the actual primary source, and it never writes the matrix product out, only "weighted linear sums".

SECOND HALF REFUTED. The "if and only if" appears in neither source; it is the claimant's inference, and the spec contradicts it in both directions. (1) "only if" fails: §3.7.3.3 says "Unused joint values (i.e., joints with a weight of zero) SHOULD be set to zero" — SHOULD, not MUST — so joints (5,0,0,0)/weights (1,0,0,0) and joints (5,7,0,0)/weights (1,0,0,0) are both conformant and deform identically with different joint indices. Likewise the four influences can be permuted, or spread into a zero-weighted JOINTS_1/WEIGHTS_1 set, with identical results. Identical data is sufficient, not necessary. (2) "if" fails because joint indices are not skeleton-global: "The JOINTS_n attribute data contains the indices of the joints from the corresponding skin.joints array". Two meshes on the same skeleton that reference different skin objects — different joints ordering, or different inverseBindMatrices — map identical index values to different joint matrices, so identical seam data deforms differently. The condition has to be "the same skin (or skins with identical joints order and inverse bind matrices)". (3) "purely from its own position" is also wrong in glTF: §3.7.2.2 "Displacements for POSITION, NORMAL, and TANGENT attributes are applied before any transformation matrices affecting the mesh vertices such as skinning or node transforms", and §3.8 "the node's weights array property overrides mesh's default morph target weights" — morph weights live per node, so two nodes with identical stored seam positions and identical skin data still separate at the seam when their morph weights differ. (4) Minor: inverseBindMatrices is OPTIONAL, so that term is identity when absent — consistent with the formula, not a contradiction.
